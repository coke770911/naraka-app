# Naraka 星格監控工具

**版本 1.2.11**

監控 Steam 社群市場（appid `1203220`）上「謫星 / Star」系列商品的新上架，
依**每個物品各自設定**的**價格上限**與**星格（Constellation）條件**篩選，
命中時同時送出

- **Telegram 訊息**（Bot API）
- **Windows 桌面通知**（plyer Toast）
- **工作列按鈕閃爍**（視窗切回前景自動停止）

桌面程式為 Python + CustomTkinter（強制深色模式），爬蟲跑在獨立執行緒，
不會卡住介面。

## 程式用途

### 解決什麼問題

《絕區零》以外的「謫星（Star）」系列商品在 Steam 社群市場上會被低價轉手，
但挂單數動輒數十筆、價格與星格品質參差，需要有人一直盯著。這個工具做三件事：

1. **自動巡檢** — 依設定的間隔反覆抓取市場頁，比對星格條件
2. **條件篩選** — 每個物品各有一組條件，只挑符合它自己門檻的挂單
3. **即時通知** — Telegram + Windows 桌面通知，立刻通知，不會被洗版洗掉

### 適用對象

- 在收購特定星格排列的謫星商品，需要在低價出現的第一時間出手
- 已經用腳本或瀏覽器擴充功能手動查，但想要一個不佔資源的常駐小工具

### 不做的事

- 不自動購買、不模擬任何 Steam 帳號操作（純讀取公開市場頁）
- 不代理、不轉售、不繞過任何 Steam 的存取控制

## 快速開始

```powershell
# 1. 建立虛擬環境
python -m venv .venv
.\.venv\Scripts\Activate.ps1

# 2. 安裝依賴
pip install -r requirements.txt

# 3. 執行
python main.py
```

使用流程：**監控清單** 輸入商品名稱（或直接貼市場網址）→ 對該物品按 **⚙ 條件**
→ 在 **物品條件** 設定它的價格上限與星格門檻 → 左側 **▶ 啟動監控**
（或 **⟳ 單次掃描** 先試跑一次看有沒有命中）。

> 從 1.0.0 升級的話，原本的全域條件會自動分發給每個物品，但 **格數會設為
> 預設的 4 格** —— 舊的那份 3 格條件對 4 格商品本來就是錯的，保留只會延續錯誤。
> 價格上限與各格門檻會照原樣搬過去，但門檻值是照 3 格商品定的，
> 第一次掃描後記得依實際資料調整。

## 條件規則

> **每個物品各自一份條件。** 各商品的星格數與價格區間差異很大 ——
> 實測 `Shadow Scent` 是 3 格、約 NT$4,000，`Novaburst` 是 4 格、
> 約 NT$47,000。用同一份條件套所有商品會誤判，所以條件是綁在物品上的。
>
> 在 **監控清單** 按物品右側的 **⚙ 條件** 選取該物品，
> 再到 **物品條件** 編輯它的條件。清單上每列都會顯示條件摘要。

### 價格

單一上限：`price ≤ 價格上限`。**填 `0` 代表不限價**。

### 星格格數

**每個物品必須手動指定 `3` 或 `4` 格**（新增物品預設 4 格）。

掃描時會回報實際偵測到的格數供對照，但**不會自動改寫你的設定**。
指定格數與實際不符時該物品會 **0 筆命中** 並在日誌警告 —— 寧可漏報，
也不拿 3 格門檻去套 4 格資料。

### 星格（Constellation）

| 格數 | 第 1 格 | 第 2 格 | 第 3 格 | 第 4 格 |
| --- | --- | --- | --- | --- |
| 3 格 | 0~9999 | 0~9999 | **0 或 1（精確）** | — |
| 4 格 | 0~9999 | 0~9999 | 0~9999 | **0 或 1（精確）** |

每格可填「下限」與「上限」：

- **留空 → 不關心這格**，不列入判定（舊版的 `-1` 會在讀入時自動轉為留空）
- 上限留空或填 `0` → **只要 ≥ 下限**就算符合
- 上限 > 0 → 必須落在 `[下限, 上限]` 區間內（最後一格除外）

#### 最後一格是絕對匹配

最後一格是 0/1 二元位，**一定要中，且不接受 AND/OR 稀釋**：

- 填 `0` → 只接受資料末格為 `0`；填 `1` → 只接受 `1`
- **留空 → 不關心**，此時末格不強制
- 末格的上限欄位不顯示也不生效（只做精確比對）

也就是說，`OR` + 「最少符合格數 2」**不能**救回末格不符的商品。
舊版會出現「前三格全中、末格 0 卻仍然通知」的情況，已修正。

#### 中間格的匹配邏輯

最後一格不列入計數，中間格（3 格 → 第1、2 格；4 格 → 第1、2、3 格）走：

- `AND`：中間格**全部**都要符合
- `OR`：中間格符合數 ≥ 「最少符合格數」（上限為格數減一；中間格有留空時
  會自動夾到實際檢查的格數）

範例（3 格、AND、末格填 `1`）：`9650 | 950 | 1`
→ 第1格 9650 ≥ 9500 ✓、第2格 950 ≥ 950 ✓、第3格 1 == 1（必中）✓

同一筆資料若末格是 `0` → **不命中**，不會因為前兩格都符合而被 OR 放行。

### 新增物品的預設

新加入的物品採 **寬鬆預設**：不限價、4 格、星格門檻全部留空，
掃描時會全部命中 —— 讓你先看到實際資料長什麼樣，再自己收緊門檻。

編輯好某個物品的條件後，按 **設為新增物品預設** 可把它設為之後新增物品的模板。

## Telegram 設定

1. 在 Telegram 找 [@BotFather](https://t.me/BotFather)，`/newbot` 建立 Bot，拿到 **Token**
2. **先對你的 Bot 傳一句訊息**（這是取得 Chat ID 的必要步驟）
3. 回到程式的「全域設定 → Telegram 通知」，填入 Token，按 **取得 Chat ID**
4. 按 **發送測試訊息** 驗證

Token 與 Steam Cookie 會以密碼形式（`●`）顯示並保存在本機 `config.json`；
Chat ID 不是憑證，為方便辨識直接顯示。

## Steam 驗證（選填）

未登入通常仍可讀取公開市場，Cookie 可以留空。若遇到 HTTP 429 或被導向
驗證頁，再從瀏覽器取得以下 Cookie 填入：

- `steamLoginSecure`
- `sessionid`

取得方式（Chrome / Edge 通用）：

1. 開啟 `https://steamcommunity.com/market/`，確認已登入
2. 按 F12 → **Console**，貼上這行按 Enter：
   ```javascript
   copy(document.cookie.match(/steamLoginSecure=[^;]+|sessionid=[^;]+/g).join('\n'))
   ```
3. 直接貼進程式的 Cookie 欄位

或走 F12 → **Application** → Storage → Cookies → `https://steamcommunity.com`，
複製 `steamLoginSecure` 與 `sessionid`。

> `steamLoginSecure` 是 JWT，約 24 小時到期，過期後重貼一次即可。
> 實測真正決定身分的是 `steamLoginSecure`，`sessionid` 只是搭著。
>
> Cookie 等同你的登入憑證，誰拿到就能登入你的帳號。程式只把它存在
> 本機 `config.json`（已列入 `.gitignore`），不會外傳。

> [!WARNING]
> **絕對不要把 Cookie 或 Token 貼到公開場所。** 包含 GitHub issue、截圖、
> 公開聊天頻道、連同錯誤訊息一起貼出的日誌。本專案是公開的 GitHub 倉庫，
> 這些內容一旦外流就等同帳號被交出去。
>
> 回報問題前請先：
>
> 1. 把 `config.json` 裡的 `telegram.token`、`telegram.chat_id` 與
>    `steam.cookies` 清空（僅供重現問題時用）
> 2. `crawler.log` **不含**任何憑證，可以放心貼；但仍含你的監控紀錄與價格，
>    介意請先自行刪掉
>
> `steamLoginSecure` 是 JWT 且會過期，外流後除了立刻改密碼，也務必確認有
> 啟用 Steam 的「受保護的 Steam 帳號（2FA）」並檢查已授權裝置清單。

## 請求節流與容錯

| 機制 | 行為 |
| --- | --- |
| 全域請求間隔 | 預設 1.5 秒以上才送出下一個請求 |
| 物品 / 分頁延遲 | 預設 2~5 秒隨機 |
| 429 或 5xx | 依 `Retry-After` 或 30/60/120 秒（+ jitter）退避重試，最多 5 次 |
| 退避耗盡 | 進入 10 分鐘冷卻，期間略過整輪掃描並於狀態列顯示倒數 |
| 分頁停止 | 達 `total_count`，或連續 2 頁沒有新的 listing 序號 |

價格上限直接與實際抓到的掛單價格比對，不另外預先查價。

> 請勿把請求間隔調得過小，過快容易觸發 Steam 限速。

### 執行緒模型

背景執行緒 **完全不碰 tkinter**，只呼叫 `bridge.post()`（`queue.Queue.put` 是
thread-safe）；主執行緒以 `after(80ms)` 迴圈 drain 佇列後才更新元件。
桌面通知也經由 bridge 交回主執行緒執行。
爬蟲讀設定走 `ConfigStore.snapshot()`（回傳 deep copy），寫入走
`ConfigStore.mutate()`（同一把鎖），因此不會讀到改到一半的設定。

### 資料流

```
Steam 頁面 HTML
  → extract_render_context()   取出舊 JSON.parse 或新版 #valve-ssr-data 容器
  → parse_ssr_page()           遍歷 queryData → pages[] → listings[]
  → parse_listing_object()     bbcode（中文欄位）→ Listing
  → _detect_slot_count()       本物品實際的星格格數（3 或 4）
  → evaluate_listing()         該物品自己的價格 + 星格條件 → (matched, reasons)
  → NotifyDedupe.observe()     同序號同價略過；改價重新通知
  → Notifier                   Telegram + 桌面通知
```

### 為什麼不做「最低價預檢」

原本設計是先打 `market/search/render` 取最低價，價格超標就整件商品跳過詳細爬取，
省下請求。實測發現該端點的 `sell_price` 與列表頁價格單位不一致（同一件商品
`search` 回 12478、列表頁顯示 `NT$4,032`），且 `currency` 參數被 Steam 忽略。
若拿它跟價格上限比較，價格上限設低時會**整批靜默漏報**，所以改為直接比對
實際抓到的掛單價格。

### 為什麼條件要掛在物品上

最初設計是全域一份條件（單一價格上限 + 逐格門檻），套用到所有監控物品。
實測各商品差異很大：

| 商品 | 星格數 | 價格區間 |
| --- | ---: | --- |
| `Star - Shadow Scent(Non-CN)` | 3 格 | NT$3,989 ~ 4,744 |
| `Star - Aegis Reckoning(Non-CN)` | 4 格 | NT$12,203 ~ 25,733 |
| `Star - Fading Polaris(Non-CN)` | 4 格 | NT$35,452 ~ 35,662 |
| `Star - Novaburst(Non-CN)` | 4 格 | NT$43,479 ~ 50,902 |

四個裡三個是 4 格、價格差到 12 倍。共用一份條件會讓 4 格商品拿 3 格門檻去比，
結果是雜訊而不是命中。條件因此改為 `ItemEntry.criteria`，由使用者在
條件頁針對每個物品設定。

格數**每個物品手動指定**（3 或 4，新增物品預設 4）。曾經做過「自動偵測」，
但那會讓同一份門檻在兩種寬度間被套用到不同位置 —— 3 格資料的第3格是二元位，
不是 4 格資料的第4格，條件跟著寬度飄移等於比錯格子。

### 格數不符時為什麼不命中

指定 4 格但實際是 3 格時，該物品會 0 筆命中並在日誌警告。另一種做法是
「以實際格數為準繼續比」，但那等於拿 3 格門檻去套 4 格資料的第3格 ——
結果看似合理、其實比錯位置。寧可漏報也不給錯的命中。

掃描仍會把偵測到的實際格數回報到條件頁（相符時顯示「與設定相符」，
不符時顯示 ⚠），但**不會自動改寫你的設定**。

### 版本與 Git 規則

- 每次修改必須同步遞增 `naraka/__init__.py` 的版本號、更新本表，並在驗證後建立 Git commit。
- 一般修改遞增 patch，例如 `1.2.0` → `1.2.1`；累積到 `.19` 後，下一次改為升第二段版本，例如 `1.2.19` → `1.3.0`。
- 預設只 commit，**僅在使用者明確要求時才 push GitHub**。
- `.exe` 僅在使用者要求時重建；Python 程式修改執行相關測試，文件修改則執行必要內容檢查。

## 疑難排解

| 現象 | 處理方式 |
| --- | --- |
| 日誌出現「Steam 限速冷卻中」 | 正常保護行為，等冷卻結束；建議再把請求間隔調大 |
| 日誌出現「找不到 Steam SSR 資料」 | Steam 可能再次改版或要求登入；先確認 Cookie，再回報 issue 附上新版頁面結構 |
| 取得 0 筆掛單 | 商品名稱可能不精確，確認網址的 `market_hash_name` 有對上 |
| 桌面通知沒出現 | 確認「啟用 Windows 桌面通知」有開；Windows 設定 → 系統 → 通知 → 允許應用程式通知 |
| 同一掛單一直重複通知 | 按「清除已通知紀錄」可重置；正常情況下會記住序號與最後通知價格，只有價格變動才會再次通知 |
| 中文顯示為方框 | 系統缺少微軟正黑體（Microsoft JhengHei），字體會自動退回預設 |
| 某物品一直 0 筆命中，日誌出現「實際掛單是 N 格」 | 格數選錯了。到「物品條件」把格數改成實際的格數 |
| 掃描筆數仍比網頁少 | 只有「星格欄位整個缺失」的掛單會被略過（欄位格式被 Steam 改掉時才會發生），可在 verbose 日誌比對；若筆數差很多請回報 issue 附上頁面結構 |
| 程式開不起來並顯示讀取設定失敗 | `config.json` 被鎖住或權限不足（常見於 OneDrive／防毒軟體剛好掃描）。關閉占用該檔的程式後重開即可，**設定不會遺失** —— 這種情況下程式不會動你的檔案 |

## 版本紀錄

### 1.2.11

- **改價再次通知**：已通知過的掛單會記住最後通知價格；序號相同且價格相同時略過，
  價格上升或下降時均再次發送 Telegram、桌面通知與工作列提醒。通知與日誌會顯示舊／新價格。
- **舊紀錄平滑遷移**：舊版僅有序號的已通知紀錄會在首次遇到時靜默記錄價格，不會因升級而重發全部舊掛單。

### 1.2.10

- **命中時閃爍工作列**：命中一筆掛單後，工作列上的程式按鈕（含圖案）會持續閃爍，
  提示程式在背景有動靜；視窗一回到前景就自動停止，**視窗本來就在前景時完全不閃**。
- 實作是 `user32!FlashWindowEx`（`FLASHW_TRAY | FLASHW_TIMERNOFG`），非 Windows 平台
  或 API 不可用時靜默略過，不影響 Telegram 與桌面通知。
- 新增獨立開關「命中時閃爍工作列」（預設開啟），**與「桌面通知」開關互不影響**：
  關掉桌面通知仍會閃。舊設定檔沒有此欄位時自動視為開啟，`version` 不變。

### 1.2.9

- **支援 Steam 新版市場頁**：Steam 已將 `renderContext` 從
  `window.SSR.renderContext=JSON.parse(...)` 改放到
  `<script id="valve-ssr-data" type="application/json">`。解析器現同時支援兩種
  容器，後續 `queryData → market_item_search → listings` 流程不變。

### 1.2.8

- **JSON 備援相容性與診斷改善**：舊版 `/render/` 端點加入 `Referer`、
  `X-Requested-With: XMLHttpRequest` 與 JSON `Accept` 標頭。若仍非 JSON，日誌會
  輸出 HTTP 狀態、Content-Type、回應大小、HTML title 及驗證／登入／限流特徵，
  不會輸出 Cookie、Token 或完整回應內容。

### 1.2.7

- **Telegram Token 欄位可見**：可直接核對及編輯 Token；與 Steam Cookie 一樣，請勿在截圖、公開 issue 或聊天中外流。
- **SSR 失敗診斷改善**：`window.SSR.renderContext` 缺失時，日誌會接著列出舊版 JSON 備援端點的具體失敗原因（HTTP 錯誤、非 JSON、缺少掛單欄位或資料解析失敗），方便判斷是 Steam 驗證、限流或頁面改版。

### 1.2.6

- **Steam Cookie 欄位可見**：全域設定的 `steamLoginSecure` 與 `sessionid`
  不再以密碼字元遮蔽，可直接核對及編輯內容；請避免在截圖、公開 issue 或聊天中外流。

### 1.2.5

- **設定檔不會再被誤判成損壞**：原本 `_read()` 用 `except Exception` 一律
  當成檔案損毀，於是「被鎖住／權限不足／同步軟體剛好掃描」這種暫時性的讀取
  失敗，會讓 `config.json` 被改名成 `.json.broken`、設定憑空消失，而且下一次
  存檔還會把預設值蓋上去。現在讀取失敗會直接報錯（原始檔完全不動），只有
  JSON 真的損毀或形狀不對才會改名保留。
- **README 加上 Cookie／Token 警告**：公開倉庫不得在 issue、截圖或聊天中
  貼出 `steamLoginSecure` 與 Telegram Token，並列出回報問題前的處理步驟。

### 1.2.4

- **修正掃描筆數少於網頁**：解析器原本把星格為 `0000-000-0`（全零）的掛單
  當成解析失敗丟棄。實測謫星・夜影浮香頁面共 56 筆，其中 12 筆是全零星格
  （謫星數據甚至有值，只是星格尚未鑑定），丟掉後日誌只會顯示 44 筆。
- 全零星格現在會保留成 `[0, 0, 0]` 並交給條件比對。末格是絕對匹配，
  末格要求為 `1` 時這些掛單仍然不會命中；把末格設為「留空＝不關心」時也不再
  被漏報（原本會直接從解析階段消失）。
- 只有「星格欄位整個缺失」才會略過該筆 —— 這是少數情況，此時筆數仍可能略少於
  網頁顯示值。

### 1.2.2

- **修正最後一格被 OR 稀釋**：末格是 0/1 二元位，改為**絕對匹配** ——
  有填就一定要中，不會因為中間格符合數達標而被放行。這修正了
  「前三格全中、末格不符仍通知」的漏報。
- **最後一格留空 = 不關心**：不再用 `-1` 表示，留空即不關心且不強制。
  舊設定檔的 `-1` 讀入時自動轉為留空，行為一致。
- **「最少符合格數」只計中間格**：上限改為格數減一；中間格有留空時會自動
  夾到實際檢查的格數。
- **移除星格自動偵測**：格數改為每個物品手動指定 `3` 或 `4`（新增物品預設 4）。
  掃描仍會回報實際格數供對照並在不符時警告，但不會改寫你的設定。
  舊設定檔的 `slot_count: 0` 一律轉為 4。
- 條件欄位改為「留空 = 不關心」，並把末格獨立顯示，避免看起來可以被 OR 稀釋。

### 1.2.1

- 修正設定檔 `-1` 門檻在 UI 顯示為 `1` 的問題。
- 價格上限改以實際抓到的掛單價格比對，不再依賴 `market/search/render` 預檢。
